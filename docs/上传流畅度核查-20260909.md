# 上传流畅度核查（2026-09-09）

核查基线为 eab40ab、小程序 1.4.3。以下区分代码证据与真机体验，不把模拟文件操作数量当成实际网速。

## 已有教训

- `bdd638a`、`2ac9d8a` 曾改进手机端压缩恢复；`fcdccbc` 最终绕开真机压缩回调卡住的问题。当前 `completePreparationOnce` 直接将安全保存的原图设为待上传，不能为了“文件更小”重新增加上传前压缩步骤。
- `e746cd5` 去掉普通直传照片上传前的手机全图 SHA-256。当前不超过 10MiB 使用微信原生文件上传，由服务器算哈希；更大的照片才使用 4MiB 分片与持久断点。
- 2026-08-28 现场反馈要求可恢复分片、指数退避和账号隔离。优化不能删除恢复清单或把“上传到服务器”误称为“电脑已归档”。

## 本次落实

1. **避免原图重复复制。** 草稿原图存入独立账号、工程目录并带清单。进入队列时先写队列 WAL，再原子移动到队列目录。未知来源仍复制。测试证明选图到入队只复制一次；进程在移动后终止仍能用 WAL 恢复；WAL 写入失败时草稿保持原位。
2. **只写实际变化的队列记录。** 以前每次状态变化和分片断点都同步重写全部历史照片。现在逐记录比较成功写入的内容，变化立即落盘，不使用延迟写入。500 张照片加 1 个批次的测试：首次 501 次写入；单张变化从 501 次降为 1 次；状态不变为 0 次。写入失败不更新缓存，可以安全重试；重载清空缓存，允许修复旧槽。
3. **草稿清理限定为明确移除。** `discardCaptureOriginal` 校验账号、工程、专有路径与清单，不能删除相册来源、队列原图或其他账号照片；不定期扫描删除旧草稿。

## 共同完成的上传流程调整

- 选图返回后立即展示缩略图；草稿复制与原始日期读取同时进行，日期只读取最多 128KB 的文件前缀，设置 1.2 秒超时。多张日期读取并行，不能识别的明确要求补日期，不拿今天冒充。
- 删除上传槽内等待预览的步骤，先完成原图上传与批次提交，再用 2 路并发补齐预览。待恢复标记立即落盘，原有重试和账号切换保护保留。
- 模拟测试：4 张照片、上传各 100ms、预览各 1000ms，200ms 已完成原图上传与提交，预览仍在恢复。旧路径推算需要 2200ms。此数据只验证调度关系，不能作为实际网速提升比例。
- 点击上传后直接进入同步记录，查看每张照片的真实状态。已上传待电脑归档与未上传分开。

## 验证边界

最终验收包含前端全套测试、类型检查、微信生产构建及服务器/电脑同步测试，详细数量见版本交付记录。自动测试验证减少文件复制和同步写入、断点及账号保护，不代表蜂窝网络吞吐量提升了某一百分比。最终仍需同一手机、同一网络、同一组照片，对比选图首屏时间、点击上传到首个上传开始、整批上传完成时间；原图体积和网络上行带宽保持相同。
